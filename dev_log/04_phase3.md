# Phase 3 — 逐位精确的 C++ 性能优化

状态:**完成**(2026-06-12,全套件 62 passed)

## 方法论

- 基准:4 车道 × 700 卡车/h × 2 天 × 0.1s 步长 × 3 种荷载效应
  (内置 IL + 离散 IL + 影响面),BM+POT(含 PT_V)+Stats+FR 全开,
  单核,固定 seed。
- **逐位精确验证**:所有输出文件 sha256 联合哈希,每次改动后必须与
  基线完全一致(`f72ec8a15c55682b`)。
- 测量手段:perf 被内核限制(paranoid=4)、gdb attach 被 yama 限制
  → cProfile(Python/pybind 边界)+ 临时 C++ 分段插桩(用后还原)。

## 关键发现:预设的热点是错的

| 测量层 | 结果 |
|---|---|
| cProfile | 88% 时间在 `libbtls.update`(C++)内 ✓ |
| Bridge::Update 插桩 | **54 万步进循环(轴位置+影响线卷积+事件极值)只占 0.22s/6.7s** |
| 真热点 | `EndEvent` 5.78s → 其中 **POTManager 5.16s** |

原计划的「去虚函数/SIMD 影响线内核」方向对该工况无效
(实测 upper_bound 替换线性扫描 + 类型分派提升:哈希一致但 0 提速)。
**真正的瓶颈是输出事件机制的文件 IO 与深拷贝。**

## 实施的优化(全部输出逐字节一致)

1. **每事件/每效应重复打开文件**(最大头,~2.6s):
   `CEvent::writeToFile/writeEffect` 原本每事件、每效应各 open/close 一次
   (整个 run ~60 万次)。新增流引用重载,`POTManager`/`BlockMaxManager`
   每文件每 flush 只开一次;BM 车辆文件改为文件主序循环(单文件内
   字节顺序不变)。
2. **`Update(CEvent)` 按值传参** → 按引用(基类与全部 manager),
   消除每事件 ×3 manager 的 CEvent 深拷贝(~0.15s)。
3. **POT 存储深拷贝**:超过多个阈值的事件原本按效应各存一份完整
   CEvent(含车辆向量)→ `shared_ptr` 共享单份(~0.25s)。
4. 查表换 `std::upper_bound` + 热路径 `.at()`→`[]` + IL 类型分派提升
   (此工况无感,但对长离散 IL/大影响面网格是渐近改进,保留)。
5. pyproject 显式钉死 `cmake.build-type = "Release"`(原依赖默认值)。

## 结果

| 阶段 | 单核耗时 | 累计提速 |
|---|---|---|
| 基线 | 6.67s | — |
| 文件打开修复 | 4.08s | 1.63× |
| 按引用传参 | 3.95s | 1.69× |
| 共享事件存储 | 3.70s | **1.80×** |

哈希全程一致 → 输出逐字节不变。残余大头:`Vehicle::Write` 的
ostringstream 格式化(每卡车每 POT 事件)与一次必要的事件深拷贝——
优化它们要动格式化路径,风险/收益比差,止步。

## 对用户 100 年场景的合成预期

切块并行(~30×)× 单核优化(~1.8×,POT 车辆输出开启时)
→ **8–12 小时 ≈ 10–15 分钟**(30 核)。
实际倍率取决于输出配置:PT_V/BM_V 关闭时单核增益会小于 1.8×。

## 教训(记录给未来)

- 「影响线卷积是瓶颈」的直觉在事件稀疏/桥短的工况下不成立——
  **先测量**。本仓库的步进内核效率已足够;IO 机制才是欠优化区。
- 受限环境(无 perf/ptrace)下,临时分段插桩 + 哈希金标准是可靠的
  优化工作流。
